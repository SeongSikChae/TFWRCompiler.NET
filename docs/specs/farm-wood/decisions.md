# 게임 미션 풀이 스크립트 나무 단계(farm-wood) 결정

### D001 이번 작업 범위는 나무 단계 해금 3개와 operators·debug, 모두 5개다
- 단계: spec
- 질문: 다음 작업(spec 하나)에서 어느 해금까지 다룰지 정해야 했다. 지금 세이브에는 건초 10개만 있고, 다음 후보 대부분에 나무가 필요하다(덤불을 심어 얻는다). 비용은 게임 에셋(`resources.assets`)에서 읽은 값이다.
- 선택지:
  - A. 나무 단계 3개: 덤불로 나무를 모아 `expand` 2레벨(나무 20) → `for`·`get_world_size()`로 정사각형 농장 순회 → `speed` 2레벨(나무 20), `carrots`(나무 50)까지 한다.
  - B. 나무 단계 + `operators`·`debug`: A의 3개에 `operators`(건초 150 + 나무 10)와 `debug`(건초 50 + 나무 50)를 더해 5개를 한 작업으로 한다. 건초와 나무를 함께 모아야 한다.
  - C. `expand` 2레벨만: 덤불로 나무 20을 모아 `expand` 2레벨 하나만 한다.
- 결정: B
- 이유: 사용자가 고른 범위다. 한 작업에 더 많은 해금을 묶어 절차 부담을 줄인다. A는 건초가 필요한 `operators`·`debug`를 다음 작업으로 미루게 되고, C는 해금 하나마다 전체 절차를 거쳐 느려서 고르지 않았다.
- 반영: spec.md 무엇을·왜, C4

### D002 레벨 해금은 백업 근거로 `expand_2`·`speed_2` 항목으로 판정하고, 다르면 사용자 화면 확인으로 대신한다
- 단계: spec
- 질문: spec 검토 1회차 지적 3. 검토 의견은 레벨 해금의 저장 이름이 정해지지 않아 C4를 판정할 기준이 없고(특히 `speed` 2레벨은 새로 여는 것이 없어 항목이 생기지 않을 수 있다), "이전 세이브에 `speed_5`가 있었다"는 서술도 자료로 확인되지 않는다는 것이다. 확인해 보니 이전 플레이 백업 `Backup/Save0_backup1024/save.json`에 `grass_4`, `speed_5`, `expand_6`이 있고 레벨 없는 `speed`·`expand`는 없어, 레벨이 오르면 해금 이름이 `<이름>_<레벨>`로 바뀌어 저장된다는 근거가 있다.
- 선택지:
  - A. 백업 근거 + 예외는 화면 확인: 근거를 백업 파일로 적고 C4의 2레벨 판정을 `expand_2`, `speed_2` 항목으로 정한다. 실제 저장이 다르면 사용자가 해금 트리 화면에서 레벨을 확인해 알려 주고 실제 값을 기록한다.
  - B. 레벨은 화면 확인만: 레벨 없는 해금은 `save.json`으로, 두 레벨 해금은 처음부터 사용자의 화면 확인으로만 판정한다.
- 결정: A
- 이유: 파일로 확인할 수 있는 근거가 있어 그것으로 판정하고, 예상과 다를 때만 사용자 확인으로 넘긴다. B는 단순하지만 파일로 확인할 수 있는 근거를 쓰지 않아 고르지 않았다.
- 반영: spec.md 게임의 제약(레벨 해금 항목, 근거 목록), C4

### D003 기준 spec은 R6을 더하고 R5를 바꾸며 R4는 그대로 둔다
- 단계: spec
- 질문: spec 검토 1회차 지적 4. 검토 의견은 기준 spec `docs/features/farm-scripts.md`의 R4가 첫 해금 4개만 요구하는데, 이번 C4·C5가 R4·R5를 고치는지 새 요구를 더하는지 spec에 없어 작업 뒤 기준 spec 갱신 방법을 정할 수 없다는 것이다.
- 선택지:
  - A. R6 추가·R5 바꿈: R1~R3은 새 단계에도 그대로 적용한다. R5를 "쓰는 함수·문법과 대조 근거"를 포함하도록 바꾸고, R6 "`save.json` `unlocks`에 `expand` 2레벨·`speed` 2레벨·`carrots`·`operators`·`debug`가 모두 있다"를 더한다. R4는 그대로 둔다.
  - B. R4를 9개로: R4를 해금 9개 전체로 고치고 R5를 바꾼다.
- 결정: A
- 이유: 작업별로 얻은 해금을 따로 남겨 이력을 추적하기 쉽고 R4의 원래 뜻이 유지된다. B는 요구 수는 줄지만 작업마다 R4가 계속 길어져 고르지 않았다.
- 반영: spec.md 무엇을·왜(기준 spec 반영)

### D004 (D003 일부 대체) 기준 spec R4를 레벨 항목도 허용하도록 바꾼다
- 단계: spec
- 질문: D003 일부 대체. spec 검토 2회차 지적 1. 검토 의견은 D003이 "R4는 그대로 둔다"고 했지만, D002의 근거(레벨이 오르면 해금 이름이 `<이름>_<레벨>`로 바뀌어 저장되고 레벨 없는 항목은 없다)대로라면 이번 작업으로 `expand` 2레벨·`speed` 2레벨을 얻은 뒤 `unlocks`에 레벨 없는 `speed`, `expand`가 남지 않아 기준 spec R4("`loops`, `speed`, `expand`, `plant`가 모두 있다")가 실제 세이브에서 거짓이 된다는 것이다. 백업 `Save0_backup1024`에도 `carrots_2`만 있고 `carrots`는 없다.
- 선택지:
  - A. R4를 레벨 허용으로: R4를 "`loops`, `plant`가 있고, `speed`, `expand`는 그 이름 또는 레벨 항목(`<이름>_<레벨>`)이 있다"로 바꾼다.
  - B. R4는 당시 기준으로 명시: R4 문장은 두고 "farm-missions 작업 완료 당시 기준"이라고 덧붙인다.
- 결정: A
- 이유: 기준 spec은 지금 유효한 요구를 담아야 하므로 판정할 수 있는 문장으로 고친다. B는 문장 변경이 작지만 지금 세이브로 판정할 수 없는 요구가 기준에 남아 고르지 않았다.
- 반영: spec.md 무엇을·왜(기준 spec 반영의 R4 문장). D003의 나머지(R6 추가, R5 바꿈)는 그대로 유효하며, R6 문장은 2회차 지적 2에 따라 C4와 같은 예외 문장으로 맞췄다.

### D005 plan의 "나무 150" 문구는 누적 합계라는 뜻을 바꾸지 않고 분명히 적는 것으로 고친다(의도 변경 아님)
- 단계: tasks
- 질문: tasks 검토 3회차 지적 1. 검토 의견은 tasks 2회차에서 T004의 README 주의 문구를 "`speed` 2레벨·`carrots` 해금 뒤 나무 60이 남았을 때(보유량)"로 고쳤지만, 확정된 plan.md 오류·위험 항목은 "6단계에서 나무 150을 다 모은 뒤 7단계로"로 남아 README에 적을 기준이 두 문서에서 다르다는 것이다. plan 문구를 보유량으로 읽으면 이미 나무 90을 해금에 쓴 뒤에도 150이 모일 때까지 6단계를 돌리게 된다. 확인해 보니 plan의 150은 결정 1항의 누적 나무 합계(20+20+50+50+10)여서 설계는 같고 문구만 모호했다.
- 선택지:
  - A. plan 문구만 명확화: plan 문구를 "누적 150까지 모은 뒤(즉 `speed` 2레벨·`carrots` 해금 후 `debug`·`operators`용 나무 60이 남았을 때, 보유량 기준)"로 뜻을 바꾸지 않고 분명히 적는다. 내용이 바뀌지 않는 수정이라 plan 검토·확인을 다시 하지 않는다.
  - B. 의도 변경으로 plan부터 다시: 확정된 plan을 바꾸는 의도 변경으로 보고 plan 검토·확인과 tasks 검토·확인을 차례로 다시 한다.
- 결정: A
- 이유: 설계(나무 합계 150, 진행 순서)는 그대로이고 모호한 문구만 바로잡는다. 규칙(workflow/spec-driven.md 3절 3번)상 내용이 바뀌지 않는 문서 수정은 고치기만 한다. B는 가장 보수적이지만 설계가 바뀌지 않아 검토만 늘어나 고르지 않았다.
- 반영: plan.md 오류·위험 마지막 항목
