# 게임 미션 풀이 스크립트(farm) 결정

### D001 게임 실행(F5)과 해금 클릭은 사용자가 하고, 에이전트는 코드 작성·컴파일·배치와 save.json 확인만 한다
- 단계: spec
- 질문: 스크립트를 게임에서 실행하고 해금 트리에서 해금을 누르는 일을 누가 할지 정해야 했다. 조사 결과 게임에는 외부에서 실행을 시키거나 해금을 누를 통로가 없다. 실행은 게임 창의 F5(또는 실행 버튼)로만, 해금은 해금 트리 클릭으로만 할 수 있다(`unlock()` 함수는 한참 뒤의 `auto_unlock` 해금 후에만 쓸 수 있다). 화면 없이 할 수 있는 것은 세이브 폴더의 `.py` 파일 수정(게임의 파일 감시가 반영)과 `save.json`(아이템 수·해금 목록) 읽기뿐이다.
- 선택지:
  - A. 에이전트가 화면 조작: 데스크톱 화면 조작(computer use)으로 게임 창에서 F5를 누르고 해금 트리를 클릭한다.
  - B. 사용자가 직접 조작: 에이전트는 코드를 쓰고 컴파일해 세이브 폴더에 넣고, 무엇을 실행·해금할지 알려 준다. 사용자가 F5와 해금을 하고, 에이전트는 `save.json`으로 진행을 확인한다.
- 결정: B
- 이유: 사용자가 직접 실행·해금하기로 했다. B는 에이전트가 사용자의 데스크톱을 조작하지 않고, 진행 확인도 `save.json`으로 화면 없이 할 수 있다. A는 실행 중 데스크톱을 에이전트가 점유하므로 고르지 않았다.
- 반영: spec.md 무엇을·왜, C4

### D002 게임 스크립트 소스는 저장소 안 `farm/` 폴더에 둔다
- 단계: spec
- 질문: 게임용 C# 소스를 어디에 둘지 정해야 했다. 저장소 안에 두면 컴파일러 저장소의 파일 변경이 된다.
- 선택지:
  - A. 저장소 안 `farm/`: 저장소에 `farm/` 폴더를 만들어 C# 소스와 스크립트를 두고, `tfwrc`로 컴파일해 세이브 폴더로 출력한다. 커밋은 승인 뒤에만 한다.
  - B. 저장소 밖 별도 폴더: 저장소 밖(예: 다른 드라이브 폴더)에 소스를 두고 컴파일러 저장소는 건드리지 않는다.
- 결정: A
- 이유: 컴파일러와 함께 버전 관리하고, 컴파일러를 실제 게임 코드로 써 보는 예제 역할도 한다. B는 컴파일러 저장소를 건드리지 않는 장점이 있지만 소스와 컴파일러가 따로 관리되어 고르지 않았다.
- 반영: spec.md C1, C2

### D003 이번 작업 범위는 기반(farm 폴더·컴파일·배치 스크립트)과 초반 해금 4개(loops·speed·expand·plant)다
- 단계: spec
- 질문: 한 작업(spec 하나)에서 미션을 어디까지 다룰지 정해야 했다. 작업마다 spec·plan·tasks와 검토 4회를 거치므로 범위가 작으면 정확하지만 느리고, 크면 절차 부담이 줄지만 완료 조건이 넓어진다.
- 선택지:
  - A. 기반 + 초반 묶음: `farm/` 폴더·컴파일·배치 스크립트와 초반 해금 4개(loops → speed → expand → plant)를 한 작업으로 한다. 이후 미션은 단계별 새 작업으로 한다.
  - B. 기반 + 첫 미션만: 기반과 첫 해금(loops)만 하고, 이후 미션은 하나씩 각각 새 작업으로 한다.
  - C. 기반만: 이번 작업은 폴더와 스크립트만 만들고 미션은 다음 작업부터 한다.
- 결정: A
- 이유: 절차 부담과 완료 조건의 구체성 사이 균형이 맞다. B는 가장 정확하지만 해금 하나마다 전체 절차를 거쳐 너무 느리고, C는 실제 게임에서 기반이 동작하는지 확인하지 못한 채 끝나 고르지 않았다.
- 반영: spec.md 무엇을·왜, C4

### D004 C3의 대조 근거는 게임 문서 first_program.md와 unlock_tooltips.txt로 한다
- 단계: spec
- 질문: spec 검토 2회차 지적 1. 검토 의견은 C3가 생성된 `.py`를 `save.json` 해금 목록과 대조하라고 하지만, `unlocks`에는 해금 이름만 있어 어떤 함수·문법이 어느 해금에 속하는지 판정할 근거가 없다는 것이다. 근거가 될 만한 `__builtins__.py`도 지금 세이브 폴더에 없다. 확인해 보니 게임의 `builtins.py`도 함수 목록만 있고 해금과의 대응은 없어서, 이대로면 C3가 사실상 사용자 보고에만 기대는 확인할 수 없는 완료 조건이 된다.
- 선택지:
  - A. 게임 문서로 대조: 대조 근거를 `first_program.md`(처음 쓸 수 있는 명령 `harvest()`, `do_a_flip()`)와 `unlock_tooltips.txt`(해금별 예시 코드)로 정한다. 두 문서로 해금 여부를 확인할 수 없는 함수·문법은 쓰지 않는다는 제약을 spec에 더하고, C3를 이 근거로 대조하도록 고친다.
  - B. 사용자 보고만: C3에서 에이전트의 대조를 빼고 사용자의 실행 오류 보고만으로 판정한다.
- 결정: A
- 이유: 보수적이지만 실행 전에 통과·실패를 판정할 근거가 생긴다. B는 단순하지만 해금되지 않은 기능을 쓴 실수를 실행 뒤에야 알 수 있어 고르지 않았다.
- 반영: spec.md 게임의 제약 넷째 항목, C3

### D005 (D004 대체) C3의 대조 근거를 게임 EN 문서 전체(docs/first_program.md·docs/scripting·docs/unlocks)와 unlock_tooltips.txt의 설명·예시로 넓힌다
- 단계: spec
- 질문: D004 대체. spec 검토 3회차 지적 1·2. 지적 1의 검토 의견은 `tfwrc`가 모든 `.py` 첫 줄에 `# Generated by tfwrc - do not edit by hand.` 주석을 조건 없이 넣는데(`src/TFWR.Compiler/Emit/TfwrEmitter.cs`), D004의 두 문서에는 `#` 주석 문법이 없어 C3가 모든 단계에서 통과할 수 없다는 것이다. 컴파일러 변경은 범위 밖이라 이 줄을 없앨 수도 없다. 지적 2의 검토 의견은 spec이 `expand`가 이동을 연다고 전제하지만 `unlock_tooltips.txt`의 `expand` 항목에는 예시 코드가 없고 `move()`가 두 문서 어디에도 없어, `expand` 이후 이동을 쓰는 단계가 C3를 통과할 수 없다는 것이다. 확인해 보니 `docs/scripting/comments.md`는 `#` 주석을, `docs/unlocks/expand_1.md`는 `move()`와 방향 상수를, `docs/unlocks/speed.md`는 `if`와 `can_harvest()`를 그 해금으로 연다고 적고 있어, 근거를 두 문서로 좁힌 D004가 결함이었다.
- 선택지:
  - A. 근거를 게임 문서 전체로: 대조 근거를 `docs/first_program.md`, `docs/scripting/*.md`, `docs/unlocks/*.md`, `Strings/unlock_tooltips.txt`의 설명 문장·예시 코드로 넓히고, 해금과 문서를 이름이나 문서 본문의 설명으로 대응시킨다.
  - B(지적 1): 근거는 그대로 두고 컴파일러가 넣는 첫 줄 주석만 대조에서 예외로 둔다.
  - B(지적 2): `unlock_tooltips.txt`의 설명 문장까지만 근거에 넣는다.
- 결정: A(지적 1·2 모두)
- 이유: 해금별로 열리는 함수·문법을 정확히 적은 문서가 `docs/unlocks`·`docs/scripting`이라 두 지적이 한 번에 풀린다. 지적 1의 B는 주석 예외 하나만 막고 지적 2가 남으며, 지적 2의 B는 설명 문장에도 `move()`라는 이름이 없어 판정이 여전히 모호해 고르지 않았다.
- 반영: spec.md 게임의 제약 근거 목록·넷째 항목, C3
